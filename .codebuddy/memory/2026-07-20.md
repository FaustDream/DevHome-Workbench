# 2026-07-20 工作记录

## favicon 本地缓存未生效修复（v2.27.6 → v2.27.7）
- **现象**：用户反馈"快捷方式获取到后应该保存在本地，避免每次重新获取"。即 favicon 缓存形同虚设，每次都重新走 SW 抓取。
- **根因**：`js/main.js:169` 调用 `ns.openFaviconDB()` 是异步 fire-and-forget，紧接着 `ns.renderTiles()`（line 174）同步渲染磁贴触发 `loadFavicon`。此时 `faviconDB` 仍为 `null` → `getFaviconFromDB` 直接返回 `null`（永远"无缓存"），`setFaviconInDB` 直接 `return`（永远写不进）。缓存完全没工作。
- **修复**：`js/favicon.js` 中 `openFaviconDB` 改为返回缓存的 Promise 单例；新增 `_ensureDB()` 惰性确保数据库已打开（首次调用时打开、之后复用），`getFaviconFromDB`/`setFaviconInDB` 均先 `_ensureDB()` 再读写。这样无论外部何时/是否调用 `openFaviconDB`，本地缓存都能真正生效。另优化：`loadFavicon` 改为先查缓存，命中直接显示图标（不再先闪字母占位），仅无缓存才显示字母占位并去 SW 获取，避免闪动。
- **提交**：`1282111` 已 push 到 main。

## favicon 重写为真实站点图标（v2.27.5 → v2.27.6）
- **现象**：用户反馈"快捷方式自动获取的图标还是模糊的球"。根因是旧逻辑用 Google S2 / DuckDuckGo 等第三方服务作为展示源，对无 favicon 的站点返回默认地球（"球"），且上一轮 CSP/CORS 修复反而把默认地球也缓存了下来。
- **重构方案**：`js/favicon.js` 重写 `loadFavicon`，改为「字母占位 → 后台 SW 解析目标站点真实 favicon → 替换显示并缓存」。移除旧的 Google/DuckDuckGo/xinac 多级 img 源链与 `_cacheFaviconFromSrc`。
- **SW 解析**：`js/background.js` 新增 `resolveRealFavicon(domain)`（替换原 `handleFetchFavicon`）：先试约定路径 `https://<domain>/favicon.ico`，失败则拉首页 HTML 解析 `<link rel="icon">`/`apple-touch-icon`，按优先级选高分辨率图标，blob→dataURL 回传。消息分支由 `FETCH_FAVICON` 改为 `RESOLVE_FAVICON`。
- **权限变更**：`manifest.json` 的 `host_permissions` 增加 `<all_urls>`（SW 对目标站点 fetch 需 host_permission 才豁免 CORS）。⚠️ 这会导致扩展更新时出现"可读取你在所有网站上的数据"的权限警告。
- **缓存清理**：IndexedDB 版本 `TabPageFaviconDB` 由 2 升到 3，重建存储以清空旧版可能缓存的默认地球。
- **提交**：`b38b51c` 已 push 到 main。

## favicon 降级链路缺陷修复（v2.27.2 → v2.27.3）
- **缺陷**：`js/favicon.js` 中 `loadFavicon` 末尾的 `if (imgElement.complete)` 兜底块，对新建且无 `src` 的 `<img>`（`complete===true`、`naturalWidth===0`）会同步触发 `onerror()`→`tryNextSource()`，与异步的 `getFaviconFromDB().then` 再次 `tryNextSource()` 叠加，导致最高优先级源（Google128）被静默跳过、降级链错位、最终兜底可靠性下降。
- **修复**：删除该 complete 兜底块；回退链唯一启动入口收敛为 `getFaviconFromDB` 的 `.then`（无缓存）与 `.catch`（缓存异常）；每步降级补 `[降级]` 结构化日志。
- **验证**：新增 `test/favicon-degradation.test.mjs`（vm 沙箱驱动真实模块），运行通过 16/16；并在 `test/docs/` 生成 10 类测试报告（单元/自动化/功能/非功能/回归/环境/安全/静态分析/边界幻觉/覆盖率）。
- **提交**：`78669c2` 已 push 到 main。

## favicon CSP 拦截修复（v2.27.3 → v2.27.4）
- **现象**：控制台报 `Connecting to 'https://t1.gstatic.com/faviconV2?...' violates connect-src`。
- **根因**：`_cacheFaviconFromSrc` 后台 `fetch('https://www.google.com/s2/favicons?...')` 被 Google 302 重定向到 `t1.gstatic.com`（t0~t3 子域），CSP `connect-src` 对重定向目标再次校验，白名单无 gstatic 故被拦截。图片显示不受影响（img-src 含 https:），仅缓存 fetch 失败。
- **修复**：`manifest.json` 的 `connect-src` 加入 `https://*.gstatic.com/`。
- **提交**：`c3cbabf` 已 push 到 main。

## favicon CORS 拦截修复（v2.27.4 → v2.27.5）
- **现象**：CSP 放行后，控制台报 `blocked by CORS policy: No 'Access-Control-Allow-Origin' header`（gstatic 响应无 ACAO）。图标本身仍靠 `img.src` 正常显示，仅后台缓存 fetch 失败。
- **根因**：扩展**页面**的 `fetch` 走 `chrome-extension://` 源，受 CORS 限制；而 Google S2 重定向到 gstatic 的响应不带 CORS 头，无法读取响应体。原 `_cacheFaviconFromSrc` 在页面直接 `fetch` 跨域 favicon 必然被 CORS 拦截。
- **修复**：改为页面通过 `chrome.runtime.sendMessage({type:'FETCH_FAVICON'})` 交给后台 SW 代理 fetch——SW 对 `host_permissions` 覆盖域名（新增 `*://*.gstatic.com/*`）豁免 CORS，取回 blob 转 dataURL 回传，页面再写入 IndexedDB。移除原页面级 `fetch` 与 `ns.proxyManager` 分支。
- **改动文件**：`manifest.json`（host_permissions 加 gstatic）、`js/background.js`（新增 `handleFetchFavicon` + `FETCH_FAVICON` case）、`js/favicon.js`（重写 `_cacheFaviconFromSrc`）。
- **提交**：`ca01b62` 已 push 到 main。
- **注意**：需在 `chrome://extensions` 重新加载扩展并使 SW 重启，host_permissions 与 SW 代码变更不会热更新。
